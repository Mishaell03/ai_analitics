## 1. Знакомимся с новым набором данных

В учебной PostgreSQL-базе для этой темы используются две таблицы:

- `retail_order_items` — товарные позиции заказов. Одна строка соответствует **одной позиции**, а не целому заказу. Поля: `line_item_id`, `order_id`, `order_date`, `customer_id`, `product`, `category`, `quantity`, `unit_price`, `status`.
- `customers` — справочник покупателей. Поля: `customer_id`, `city`, `registration_date`. Каждому покупателю соответствует одна строка справочника.

В `retail_order_items` 36 товарных позиций. В ней встречаются статусы `completed` и `cancelled`. Как и прежде, **учебную выручку** рассчитываем только для завершённых позиций по формуле `quantity * unit_price`.

В таблице `customers` двенадцать покупателей с идентификаторами от `C001` до `C012`. Например:

| customer_id | city |
|---|---|
| `C001` | Москва |
| `C003` | Казань |
| `C010` | `NULL` — город неизвестен |
| `C011` | Самара |

`NULL` означает, что значение города отсутствует. Это **не** название города и **не** обозначение Москвы.

Покупатели `C011` и `C012` в рассматриваемом наборе заказов не имеют. Покупатель может встречаться в нескольких товарных позициях, и это нормально.

Условия учебной SQL-песочницы не изменились: запросы выполняются в отдельной базе, предназначенной для занятий, и доступны только операции чтения. Таблицы должны быть подготовлены заранее. Если таблица не найдена или недоступна, сообщите преподавателю: создавать её самостоятельно не требуется.

## 2. Группировка: от строк к сводке

### 2.1. Зачем нужен `GROUP BY`?

Представьте вопрос: **сколько товарных позиций имеет каждый статус?** Запрашивать все строки и считать их вручную неудобно. В pandas вы использовали группировку; SQL предоставляет похожую возможность.

```sql
SELECT status, COUNT(*) AS line_count
FROM retail_order_items
GROUP BY status
ORDER BY status;
```

**Ожидаемый результат:**

| status | line_count |
|---|---:|
| cancelled | 4 |
| completed | 32 |

Разберём запрос по частям:

1. `FROM retail_order_items` — читаем товарные позиции нового набора.
2. `GROUP BY status` — объединяем строки с одинаковым статусом в группы.
3. `COUNT(*)` — считаем **строки** в каждой группе.
4. `AS line_count` — даём вычисляемому столбцу понятное имя. Это **псевдоним**, или *алиас*.
5. `ORDER BY status` — располагаем группы по названию статуса.

Сводка содержит две строки, а не 36: каждая представляет **группу**. Обратите внимание: `COUNT(*)` считает товарные позиции, а не уникальные заказы или проданные единицы.

### 2.2. Отбираем записи **до** группировки

При анализе продаж отменённые позиции учитывать нельзя. Сначала зададим `WHERE`, затем сформируем группы.

```sql
SELECT category, SUM(quantity) AS units_sold
FROM retail_order_items
WHERE status = 'completed'
GROUP BY category
ORDER BY category;
```

Здесь `WHERE status = 'completed'` исключает отменённые позиции, а `SUM(quantity)` складывает количества внутри каждой категории.

Важное отличие:

- `COUNT(*)` — **сколько строк-позиций** попало в группу.
- `SUM(quantity)` — **сколько единиц товаров** содержится в этих позициях.
- `SUM(quantity * unit_price)` — **какова учебная выручка** группы.

Одна позиция может содержать несколько единиц товара. Поэтому количество строк и сумма количеств — разные показатели.

**Правило записи:** если вы выводите вместе со сводным показателем обычный столбец (например, `category`), он, как правило, должен присутствовать в `GROUP BY`. Запрос, который выводит `category`, `product` и `SUM(quantity)` только с `GROUP BY category`, неправильно устроен для этого учебного случая: PostgreSQL не знает, какое отдельное `product` показать для всей категории.

### 2.3. Рассчитываем выручку группы

Вы уже умеете суммировать выручку всех завершённых позиций:

```sql
SELECT SUM(quantity * unit_price) AS total_revenue
FROM retail_order_items
WHERE status = 'completed';
```

Результат: **302780 рублей** учебной выручки.

Чтобы получить показатель **по группам**, используем то же выражение `SUM(quantity * unit_price)`, но добавляем группировку по нужному признаку. Например, группировка по `category` сформирует отдельную сумму для каждой товарной категории, а `ORDER BY ... DESC` позволит расположить категории по убыванию выручки.

В `ORDER BY` можно перечислить несколько ключей через запятую. Сначала PostgreSQL сортирует по первому ключу, а при равенстве значений — по следующему. Для каждого ключа направление задаётся отдельно: `DESC` — по убыванию, `ASC` — по возрастанию. В сортировке можно использовать псевдоним вычисленного показателя.

В следующей самостоятельной практике вы составите полный запрос для такого сравнения. Помните, что **выручка не равна прибыли**: в нашей модели не учитываются расходы, себестоимость и другие финансовые составляющие.

### 2.4. Бесплатная позиция — не обязательно ошибка

В новом наборе есть товарная позиция `line_item_id = 28`: количество 1, цена единицы 0. Это допустимый бесплатный товар. В том числе и завершённая бесплатная позиция должна участвовать в подсчёте строк и единиц, если соответствует условиям запроса. Её вклад в денежную выручку при этом равен нулю.

**Нельзя автоматически удалять записи только потому, что `unit_price = 0`.** Количество по правилам набора должно оставаться положительным.

## 3. Почему сведения хранятся в разных таблицах?

В `retail_order_items` уже есть `customer_id`, но нет города покупателя. Город хранится в `customers`. Это позволяет не повторять название города в каждой товарной позиции одного покупателя.

Связь строится по `customer_id`:

- `customers.customer_id` — уникальный идентификатор покупателя, ключ справочника.
- `retail_order_items.customer_id` — ссылка на покупателя; такое поле называют внешним ключом по смыслу связи.
- **Один покупатель → много товарных позиций:** один и тот же `customer_id` в продажах может встречаться многократно.

Таблица `orders` содержит данные об отдельных заказах (`order_id`, `customer_id`, `sales_channel`), а `products` — данные о товарах (`product`, `brand`, `supplier`). Сегодня для первого объединения достаточно **двух** таблиц: `retail_order_items` и `customers`.

### 3.1. `INNER JOIN`: соединяем совпадающие записи

```sql
SELECT
    roi.line_item_id,
    roi.customer_id,
    c.city
FROM retail_order_items AS roi
INNER JOIN customers AS c
    ON roi.customer_id = c.customer_id
ORDER BY roi.line_item_id;
```

Что означает каждая новая часть:

1. `AS roi` — короткое имя таблицы `retail_order_items`.
2. `AS c` — короткое имя таблицы `customers`.
3. `INNER JOIN` — соединяет строки, для которых найдено совпадение по указанному правилу.
4. `ON roi.customer_id = c.customer_id` — **правило сопоставления** двух таблиц.
5. `roi.line_item_id` и `c.city` — точная запись того, из какой таблицы взять поле.

Результат добавляет к сведениям о каждой найденной товарной позиции город соответствующего покупателя. **Повторение одного покупателя в разных строках продаж нормально:** это разные товарные позиции, связанные с одним человеком.

В этом учебном наборе покупатели в продажах имеют соответствующие записи в справочнике, а ключ `customers.customer_id` уникален. Поэтому при правильном соединении каждой товарной позиции соответствует ровно одна строка справочника.

Если совпадающего покупателя в `customers` не было бы, `INNER JOIN` **исключил бы** такую товарную позицию из результата. Если бы один и тот же `customer_id` ошибочно повторялся в справочнике, одна позиция могла бы появиться несколько раз. Оба случая способны исказить расчёты.

### 3.2. Отсутствующий город не означает отсутствие продажи

Покупатель `C010` существует в справочнике, но его `city` имеет значение `NULL`. У него есть завершённая товарная позиция с учебной выручкой 460 рублей.

Такая строка **успешно соединяется** по `customer_id`: отсутствие города не означает отсутствие покупателя. При группировке по `c.city` строка попадёт в отдельную группу с меткой `NULL`.

**Группа `NULL` означает «город неизвестен».** Её нельзя автоматически относить к Москве или выбрасывать из общей суммы. Результаты по известным городам не охватывают всю выручку.

Также «выручка по городу покупателя» не равна «выручке по месту доставки» — такого вывода эти данные не позволяют сделать.

### 3.3. Проверяем, не удвоились ли продажи после соединения

Проверим контрольный показатель сначала **без соединения**:

```sql
SELECT SUM(quantity * unit_price) AS completed_revenue
FROM retail_order_items
WHERE status = 'completed';
```

Теперь повторим расчёт **после соединения**:

```sql
SELECT SUM(roi.quantity * roi.unit_price) AS completed_revenue
FROM retail_order_items AS roi
INNER JOIN customers AS c
    ON roi.customer_id = c.customer_id
WHERE roi.status = 'completed';
```

При корректном наборе данных оба запроса возвращают **302780 рублей**. Если суммы различаются, нужно проверить соединение: не потерялись ли строки и не размножились ли они из-за совпадений с несколькими записями справочника.

Совпадение сумм — полезная проверка, **но не доказательство идеальной корректности всех связей**. Ошибки в отдельных строках могут взаимно компенсироваться, поэтому важны и правильные ключи, и уникальность справочника.

## 4. Разберём пример: продажи покупателей из одного города

**Задача:** узнать, сколько завершённых товарных позиций и какую учебную выручку принесли покупатели с записанным городом «Москва».

Сначала определяем нужные таблицы: статус, количество и цену берём из `retail_order_items`, а город — из `customers`.

```sql
SELECT
    COUNT(*) AS completed_lines,
    SUM(roi.quantity * roi.unit_price) AS revenue
FROM retail_order_items AS roi
INNER JOIN customers AS c
    ON roi.customer_id = c.customer_id
WHERE roi.status = 'completed'
  AND c.city = 'Москва';
```

**Ожидаемый результат:**

| completed_lines | revenue |
|---:|---:|
| 12 | 123030 |

Разбор:

1. `INNER JOIN` добавляет к товарным позициям сведения о покупателях.
2. `WHERE` отбирает только завершённые позиции покупателей, у которых в справочнике указан город Москва.
3. `COUNT(*)` считает **позиции**, а не покупателей и не заказы.
4. `SUM(roi.quantity * roi.unit_price)` даёт учебную выручку этих позиций.

Теперь вы знаете, как связать таблицы, отобрать нужные записи и посчитать показатель. **Следующий шаг — вместо одного города получить отдельную строку для каждого города:** для этого вы самостоятельно примените `GROUP BY c.city`.

## 7. Итоги урока

Сегодня вы освоили две основные возможности аналитического SQL:

- **`GROUP BY`** объединяет строки в группы, для которых можно посчитать `COUNT()` или `SUM()`.
- **`INNER JOIN ... ON`** соединяет записи из разных таблиц по общему ключу.

Вы также научились использовать `AS` для понятных имён результатов, применять `WHERE` до агрегации, сортировать сводки и проверять суммы до и после соединения.

Особенно важно помнить три правила:

1. **Товарная позиция, заказ, проданная единица и выручка — разные показатели.**
2. **Повторы идентификатора покупателя в продажах нормальны**, а неправильная связь или повтор ключа в справочнике может привести к двойному учёту.
3. **Неизвестный город не отменяет покупку:** группа `NULL` должна оставаться в учёте общей выручки.

В следующем уроке вы научитесь представлять рассчитанные показатели на графиках, чтобы делать сравнения и выводы более наглядными.
