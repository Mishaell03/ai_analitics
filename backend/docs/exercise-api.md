# API заданий ученика

Базовый путь:
`/api/v1/courses/{course_slug}/modules/{module_id}/lessons/{lesson_id}/exercises`.

- `GET /` — задания опубликованного урока, язык, доступность выполнения и личный прогресс.
- `GET /{exercise_id}` — одно задание.
- `POST /{exercise_id}/submit` — выполнение и проверка кода.

Все запросы требуют существующей сессии и записи на курс. Проверяется принадлежность
модуля курсу и урока модулю. Администратор не обходит запись на курс в этом API.
Ответы из `exercise_answers` не входят в публичное представление задания.

## Описание задания

Язык задаётся автором в Markdown урока сразу после `id:`:

```text
:::test
id: print-number
language: python
Выведите число 42.
:::
```

Допустимы ровно `language: python` и `language: sql`. Без заголовка задание
остаётся обычным тестом, выполнение для него запрещено. Дублирующиеся ID
отклоняются. Текст Markdown публичный: решения и скрытые проверки туда не помещают.

Для Python необходимы существующая запись `ExerciseAnswer` с этим ID и разрешённый
профиль в `SANDBOX_ASSIGNMENT_PROFILES`. `execution_enabled` отражает разрешение
в конфигурации, а не оперативную доступность runner.
Старый `POST /api/v1/sandbox/execute` также проверяет наличие задания в Markdown
и язык; для прежних заданий понадобится добавить явный заголовок языка.
Этот endpoint только выполняет код, без сохранения попытки.

Запрос отправки:

```json
{"language":"python","code":"print(42)"}
```

Язык запроса должен совпадать с языком задания. Профиль, пользователь, лимиты,
параметры подключения и дополнительные поля в запросе запрещены.

## Результат и прогресс

Ответ содержит `execution` (существующий контракт stdout/stderr/exit_code/лимиты),
`execution_succeeded`, `is_correct` и `attempt_id`.

- Успешное выполнение не означает правильный ответ.
- Проверка использует существующий `ExerciseCheckService.answers_match`: точное
  сравнение отправленного кода с ответом `{"type":"code","value":"..."}`
  либо legacy-строкой. Семантически эквивалентные программы могут не совпасть.
- Эталон не выполняется и не передаётся в sandbox. Test-based grader в проекте
  отсутствует; stdout не используется как доказательство правильности.
- При ошибке выполнения, timeout, OOM или усечении вывода `is_correct=null`.
- Завершившееся выполнение сохраняется в `LessonAttempt`; только правильный ответ
  попадает в `__passed_exercises__` с correctness=2. Завершение урока остаётся
  обязанностью существующего endpoint подтверждения всех заданий.
- При недоступности runner/отказе доступа попытка не создаётся.
- Существующий `/check` сохраняет прежнюю семантику проверки ответа без запуска.

## Ограничения выполнения

Python запускается через существующий отдельный HTTP runner, в новом контейнере
без сети, секретов и томов хоста, с read-only root и ограничениями CPU, RAM,
PID, времени, временных файлов и вывода. См. `infra/sandbox/README.md`.
Runner ограничивает общий параллелизм (3, heavy — 1) и выполняет очистку после
ошибки/отмены. HTTP-клиент дополнительно ограничен общим deadline.
На пользователя допускается 10 запусков в минуту **на worker API**; это локальный
rate limit, не распределённая квота. Глобальный предел контейнеров остаётся в runner.
Для нескольких workers строгая пользовательская квота требует общего хранилища.

Код ограничен 64 KiB UTF-8, тело запроса ограничивается до JSON parsing.
Тело запросов выполнения не кэшируется middleware для error log; стандартный
обработчик validation errors всё ещё может логировать некорректные входные значения.
Не передавайте секреты в учебный код. stdout/stderr должны отображаться клиентом
как текст, а не HTML.

## SQL: выполнение заблокировано

SQL-язык распознаётся, но выполнение возвращает **503 `SQL_SANDBOX_UNAVAILABLE`**.
Нет SQL-соединения, SQL-пула или fallback к прикладному engine. Даже `SELECT 1`
не выполняется. Это ограничение реализации, а не работающий SQL runner.

Подготовленный init-скрипт создаёт учебную БД на общем PostgreSQL, но его аудит
не гарантирует изоляцию от прикладных БД и безопасность вызываемых функций.
Перед реализацией/включением SQL требуется согласование отдельного экземпляра
PostgreSQL без прикладных данных, ограниченной роли, сетевой изоляции и внешних
лимитов ресурсов. Runner должен дополнительно проверять PostgreSQL AST, разрешать
только одобренные объекты/функции и одну read-only команду, применять transaction/
statement/lock deadlines, ограничивать строки и байты при потоковом чтении,
отменять запросы и очищать соединения. См. также раздел SQL Runner в `README.md`.

В этой работе конфигурация окружения, deployment, секреты и миграции не менялись;
SQL init-скрипты не запускались. Требуется одобрение инфраструктуры SQL.

## Проверки

Из `backend/`:

```bash
venv/bin/python -m pytest tests/test_student_exercises.py tests/test_sandbox.py tests/test_exercise_check.py tests/test_lesson_completion.py tests/test_markdown_parser.py tests/test_request_body_middleware.py tests/test_csrf.py -q
```

Реальные Docker-тесты запускаются отдельно при остановленном runner и отсутствии
активных заданий; используют готовый образ, не затрагивают PostgreSQL:

```bash
SANDBOX_DOCKER_TESTS=1 venv/bin/python -m pytest tests/test_sandbox_docker.py -q
```
